# 淘宝直播多表查询

## 查询决策流程

1. 先判断是否存在会实质改变 SQL、指标口径、数据粒度或结论的歧义；存在时按“澄清规则”处理，否则直接进入 Schema 检索。
2. 使用用户的原始问题调用 `db_schema_search`，从服务端维护的 Schema 索引中选择候选表。
3. 对候选表调用 `db_get_table_profile`，默认设置 `include_samples=false`，先依据字段、索引、外键和表描述确认结构。
4. 只有候选表语义仍不清楚且样例确有助于判断时，才对相关表再次调用 `db_get_table_profile` 并设置 `include_samples=true`；不要为所有候选表默认读取样例。
5. 需要多张表时调用 `db_get_join_paths`，确认存在明确关联路径后再规划 JOIN。
6. 使用明确列名编写只读 MySQL `SELECT` SQL。
7. 调用 `db_validate_sql` 校验 SQL。
8. 只有校验成功后才能调用 `db_execute_sql`；时间范围分析同时传入 `quality_context`，由服务端检查
   周期覆盖、零分母、小样本和必要维度。
9. 绝不编造数据库查询结果。

`db_get_schema_ddl` 只用于诊断和检索失败后的后备：仅当 `db_schema_search` 没有返回可用
候选、搜索结果与表画像明显冲突，或用户明确要求排查 Schema 时调用。普通查询不要调用它，
也不要把它当作固定的首个工具。

数据库中的全部基础表均由工具动态发现，不把支持范围硬编码为固定表清单。对于没有预置业务
说明的表，先结合 `db_get_table_profile` 返回的字段、索引、外键和样例确认语义；存在会改变
结论的歧义时使用 `clarify`，不得仅凭表名猜测业务含义。

服务端可能在系统上下文中注入“指标公式上下文”。它是按当前问题检索出的指标公式
参考：先用候选表画像核对 `required_fields`、粒度和字段语义，再严格遵守其中的公式、聚合规则、
零分母处理和警告。字段不存在时明确说明不能计算，不得用名称相近字段替代；同一用户词命中
多种会改变结果的口径时按澄清规则处理。不要自行发明或改写已匹配的指标公式。

## 澄清规则

- 只有歧义会实质改变 SQL、指标口径、数据粒度或结论时才调用 `clarify`。
- 用户要求查询并导出，但无法判断要生成“简单查询、对比分析、诊断分析”中的哪一种时，
  这属于会改变查询范围和工作簿结构的关键歧义：必须先询问用户，并将这三项作为 choices；
  用户确认前不得调用数据库或导出工具。若用户问题本身已明确要求单值/明细、对比/趋势或
  原因/异常诊断，则直接采用对应类型，不要重复询问。
- 低风险歧义采用合理默认值，并在最终回答的“查询假设”中说明。
- 每轮最多询问一个关键问题；有清晰候选项时优先提供不超过 4 个 `choices`，不要一次提出多个问题。
- `clarify` 超时或未取得有效回答时，不执行依赖该答案的查询。

## 已知核心表粒度

- `tb_live_goods_daily_stats`：每个日期、每个商品一行（`item_id + stat_date`）。
- `tb_live_goods_session_stats`：每场直播、每个商品一行（`item_id + live_session_id`）。
- `tb_session_endtime_stats`：每场直播一行汇总（`live_session_id`）。

直播商品表通过 `live_session_id` 关联直播汇总表。将一行直播汇总数据关联到多行商品数据后，
直播层指标会被重复。因此，先聚合商品数据再关联，或确保每场直播的汇总指标只取一次。

## 业务口径

- 指标公式以服务端注入的“指标公式上下文”为优先参考，不在 Skill 中重复维护整套公式。
- 没有匹配到指标定义时，通过 Schema 检索和表画像确认字段语义；关键口径不明确时澄清，不得猜测公式。
- 来源占比字段以小数存储，回答用户时格式化为百分比。

商品粒度的买家数在不同商品之间可能重复。计算整场直播的买家数和转化率时，优先使用
`tb_session_endtime_stats`，不要直接累加商品粒度的买家数。

## 分析证据规则

- 服务端注入的 `analysis_output_contract` 决定本轮分析深度。简单查询只取必要指标；对比分析必须
  取得当前期和可靠基准期；诊断分析还必须进行可用维度拆分，形成异常或驱动证据后再给建议。
- 简单查询只回答用户要求的指标，不为填充模板额外执行无关查询。
- 用户要求趋势、变化、对比、诊断或“为什么”时，需要同时取得可靠基准；用户未指定基准时，
  默认使用等长上一周期，并在最终回答中说明。无法构造可比周期时明确说明，不得伪造变化率。
- 对比必须同时计算当前值、基准值、绝对变化和变化率；比率类指标优先比较百分点变化。
- 驱动因素必须能由维度拆分结果支持，并尽量给出贡献量或贡献占比；不能从现有字段证明原因时，
  只能标记为“待验证推断”，不得写成事实。
- 小样本、零分母、空结果、返回截断或缺少关键字段会影响结论时，必须在最终回答中显著提示。
- 建议动作必须绑定本轮查询得到的指标、异常或贡献项；没有数据依据时不输出泛化经营建议。

## 服务端数据质量上下文

- 时间范围查询调用 `db_execute_sql` 时，在 `quality_context.period_start`、`period_end` 中传入本轮
  已确定的实际日期边界，并通过 `time_column` 指定结果中的时间列。
- 聚合查询无法直接返回逐日时间列时，SQL 应同时返回以下审计列：
  `MIN(时间列) AS data_period_start`、`MAX(时间列) AS data_period_end`、
  `COUNT(DISTINCT DATE(时间列)) AS covered_days`、`MAX(时间列) AS data_freshness`。
- 分维度分析通过 `quality_context.required_dimensions` 声明结论依赖的维度；服务端会核对这些维度
  是否真实存在于结果列中。
- 比率指标通过 `denominator_columns` 指明 SQL 结果中的分母列；涉及可靠性判断的计数指标通过
  `sample_size_columns` 指明样本量列。不要传表达式或表名，只传结果列名。
- 服务端返回的 `data_quality` 是最终回答和结构化结果的唯一质量依据；无法计算的字段保持 null，
  不得由模型补齐。

## SQL 规则

- 只使用 MySQL 方言。
- 只允许只读 `SELECT`。
- 禁止使用 `SELECT *`。
- 多步骤指标使用 CTE。
- 默认最近 30 天范围使用 `CURRENT_DATE - INTERVAL 30 DAY`。
- 比率分母使用 `NULLIF(..., 0)`。
- 不要在缺少商品标识和明确日期规则时直接关联日粒度表与场次粒度表。
